# بناء الوكيل الذكي المخصص — تخطيط عميق

تخطيط لمرحلة بناء الـ Custom AI Agent لصفحة عبايات Masa Fashion على فيسبوك. الافتراض أن ManyChat هو طبقة الربط (External Request للداخل، Dynamic Block للخارج)، وأن المنطق الذكي كله يعيش في الـ Backend الخاص بك.

---

## 1. حجر الأساس: نمط "الوكيل" بدل "الرد الواحد"

القرار المعماري الأهم: لا تبني "برومبت واحد يرد على كل شيء". ابنِ **وكيلاً (Agent) يستخدم أدوات (Tool Use / Function Calling)**.

الفكرة أن Claude لا يجاوب من خياله، بل يستقبل الرسالة + السياق، ثم **يقرّر أي أداة يستدعي**: هل يبحث في الكتالوج؟ هل يتحقق من توفّر مقاس؟ هل يرسل معرض صور؟ هل يحوّل لإنسان؟ هذا بالضبط ما يجعله "ذكياً" ويتعامل مع الحالات الشاذة بمرونة بدل ما ينهار عند أول مدخل غير متوقع.

عملياً: تعرّف مجموعة دوال (موصوفة لـ Claude بصيغة JSON Schema)، وكل دالة عندك مربوطة باستعلام على قاعدة البيانات أو فعل. Claude يختار، أنت تنفّذ، وتعيد له النتيجة ليصيغ الرد. الفرق بين بوت يكتب جملاً جميلة وبين وكيل فعلاً مفيد هو هذه الطبقة.

---

## 2. التقنيات المستعملة (Tech Stack)

| الطبقة | الاختيار | لماذا |
|---|---|---|
| Backend / Runtime | Node.js + TypeScript، إطار **Next.js (App Router)** | تطبيق واحد يجمع نقطة الـ webhook + لوحة التحكم. متوافق مع خبرتك في Medusa/Mercur. |
| النموذج | **Anthropic Claude API** | رؤية (vision) + تفكير + tool use في نموذج واحد. |
| تدرّج النماذج | Haiku للتصنيف واستخراج الصفات، Sonnet للمحادثة الأساسية، تصعيد لـ Opus للحالات المعقّدة | ضبط التكلفة مع الحفاظ على الجودة. لا داعي لاستخدام أقوى نموذج لكل رسالة. |
| قاعدة البيانات | **PostgreSQL** (+ امتداد **pgvector** اختياري) | الكتالوج، الصفات، الذاكرة، الحالة. pgvector للتشابه البصري لاحقاً. |
| تخزين الصور | **Cloudinary** أو S3/R2 | روابط صور ManyChat **مؤقتة**، فتحتاج تنزيلها/إعادة استضافتها. Cloudinary يعطيك تحويلات (قصّ/تصغير) مجاناً. |
| طابور المهام | **BullMQ + Redis** (أو أخف) | لـ debounce الرسائل المتتابعة + فهرسة الكتالوج كمهام خلفية. |
| الـ embeddings (اختياري) | FashionCLIP أو SigLIP‑2 | فقط لو فعّلت "ابحث عن شبيه هذه الصورة" بصرياً. ابدأ بدونه. |

**ملاحظة مهمة على روابط الصور:** ManyChat يلتقط صورة الزبون في حقل النظام `{{last_image_url}}` ويمرّره في الـ External Request، لكنه رابط CDN مؤقّت. فأول شيء يعمله الـ Backend عند وصول صورة: ينزّلها فوراً ويعالجها (وإن احتجت تخزينها، يرفعها على Cloudinary).

## 3. البحث البصري عن المنتجات — محور طلبك

هذا قلب المشروع: "كل العبايات اللي لونها أحمر" و"الزبون يرسل صورة، جِب الشبيه". الحل **هجين**، والأبحاث الحديثة في e-commerce تؤكده: الـ embeddings العامة (مثل CLIP) ضعيفة في التقاط الصفات الدقيقة كاللون بالضبط، بينما **استخراج الصفات المُهيكلة عبر نموذج رؤية** أدقّ وأوضح لحالة "أحمر".

### أ. خط الفهرسة (Catalog Indexing Pipeline) — يتم مرة واحدة + عند كل منتج جديد

لكل منتج في الكتالوج، مرّر صورته (+ وصفه إن وُجد) على Claude vision لاستخراج **صفات مُهيكلة** وتخزينها في Postgres كأعمدة/JSONB + tags:

- `color_family` (اللون الأساسي المُقَنّن: أحمر / أسود / كحلي / بيج…) + `color_shade` (الدرجة: عنابي، خمري، وردي…)
- `sleeve_type`، `fabric`، `embellishment` (تطريز/حجر/سادة)، `style`، `occasion`، `length`
- `price`، `available_sizes`، `stock_status`، `sku`، `image_urls[]`

### ب. تقنين الألوان (Color Normalization) — ضروري للهجة الأردنية

الزبون بيقول "نبيتي" أو "عنابي" أو "خمري" وكلها تقع تحت عائلة **الأحمر الغامق**. خزّن دائماً حقلين: التسمية الخام (`نبيتي`) + العائلة المُقَنّنة (`أحمر`). هكذا استعلام "كل العبايات الحمراء" يلتقط كل الدرجات، واستعلام "نبيتي بالذات" يلتقط الدرجة المحددة. خريطة المرادفات هذه تعيش في جدول صغير قابل للتعديل من لوحة التحكم.

### ج. مساري البحث

**المسار 1 — بحث بالصفات** (طلبك: "كل العبايات الحمراء"): مجرد فلتر SQL على `color_family = 'أحمر'`. دقيق، سريع، قابل للتفسير، وقابل للدمج مع شروط أخرى ("أحمر سادة تحت ٣٠ دينار مقاس M"). هذا يغطّي ٩٠٪ من طلبات الزبائن.

**المسار 2 — بحث بصورة الزبون**: تمرّر صورة الزبون على Claude vision لاستخراج نفس الصفات → تفلتر الكتالوج بها. (اختيارياً تضيف embedding للصورة وبحث nearest-neighbor في pgvector للتشابه البصري الحقيقي "بدي شبه هاي بالضبط".) الصفات للدقّة، الـ embeddings لـ"الشكل العام".

### د. إرجاع النتائج كمعرض صور

ManyChat يدعم **Dynamic Block بصيغة v2**، ومنها نوع `cards`: معرض أفقي قابل للتمرير، كل بطاقة فيها صورة + عنوان + سعر + زر. فالـ Backend يرجّع JSON فيه نص ترحيبي + معرض البطاقات للعبايات المطابقة. **لا ترسل ٢٠ صورة دفعة واحدة** — أرسل أفضل ٣–٥ + زر "أشوفلك أكثر؟" (pagination).

## 4. تحميل سياق المحادثة (الذاكرة)

نقطة جوهرية: الـ External Request **عديم الحالة (stateless)** — كل نداء منفصل. فالـ Backend هو المسؤول عن إعادة بناء السياق من قاعدة البيانات، والمفتاح هو `subscriber_id` (الـ PSID).

**جدول المحادثات:** لكل دور (turn) سطر فيه `subscriber_id`, `role` (زبون/وكيل), `text`, `image_url`, `extracted_attributes`, `timestamp`. عند كل طلب، حمّل آخر N رسالة (أو آخر X دقيقة). للمحادثات الطويلة، احتفظ بـ **ملخص متدحرج (rolling summary)** بدل إرسال كل التاريخ، لضبط التكلفة.

**حالة الجلسة (Session State) كـ JSONB:** هنا يصير الوكيل "ذكياً فعلاً" — خزّن تفضيلات الزبون المستنتجة: اللون المفضّل، المقاس، الميزانية، الإعلان الذي جاء منه، المرحلة (تصفّح / يريد يطلب)، لغته/لهجته، وهل تم تحويله لإنسان. هكذا الرد يصير متماسكاً: "زي ما حكيتِ قبل شوي، بتدوري على عنابي مقاس M — هاي الخيارات".

## 5. سياق الإعلان (Ad Attribution) + الحالة الشاذة #1

**كيف نعرف من أي إعلان جاء الزبون:** في إعلانات Click-to-Messenger، كل إعلان/منتج يأخذ **`ref` parameter** فريداً (عبر `m.me/PAGE?ref=...`). ManyChat يلتقطه ويخزّنه في Custom Field، فتمرّره في الـ External Request. هكذا الـ Backend يعرف `ad_context` (مثلاً: "جاء من إعلان العباية السوداء المطرّزة").

**الحالة الشاذة #1 (طلبك):** الزبون جاء من إعلان منتج A لكنه أرسل صورة منتج B. عند الوكيل **إشارتان**: سياق الإعلان + النية الفعلية (الصورة/الرسالة). القاعدة الذهبية: **النية الفعلية تتغلّب على افتراض الإعلان.** يعترف بلطف ("شفتِ إعلان العباية السوداء؟ بس هاي صورة لقطعة ثانية — خليني أساعدك فيها") ويتمحور حول ما يريده الزبون فعلاً. لا يفرض منتج الإعلان أبداً، لكن يستخدم سياق الإعلان كـ **مرجّح خفيف** فقط لو كان الزبون غامضاً.

## 6. خريطة الحالات الشاذة (Edge Cases) — شاملة

تتضمن ما ذكرته + أمور لم تذكرها لكنها ستضربك في الإنتاج:

| # | الحالة | الكشف | المعالجة |
|---|---|---|---|
| 1 | تضارب الإعلان مع النية | `ad_context` ≠ محتوى الصورة/الرسالة | النية الفعلية تتغلّب؛ اعتراف لطيف وتمحور |
| 2 | صورة لمنتج خارج الكتالوج / منافس | لا تطابق قوي في البحث | "ما عندنا هاي بالضبط، بس هاي أقرب الخيارات" — لا تدّعي أنك تملكها |
| 3 | صورة ليست منتجاً (سيلفي/سكرين شوت/ميم) | استخراج الصفات يفشل أو يعطي لا‑منتج | استيضاح لطيف: "بتقصدي قطعة معينة؟ ابعتيلي صورتها" |
| 4 | عدة قطع في صورة واحدة | الرؤية تكشف كائنات متعددة | اسأل أيّها يقصد، أو عالج الأبرز |
| 5 | اللون/المقاس غير متوفر | أداة `check_availability` ترجع نفاد | اعرض البدائل المتوفرة |
| 6 | مفاصلة على السعر (شائعة بالسوق) | كشف نية تخفيض | رد مقيّد بالسياسة؛ لا خصومات غير مصرّح بها؛ اعرض التحويل لإنسان |
| 7 | نية الطلب (الدفع عند الاستلام) | كشف نية شراء | اجمع: الاسم/الهاتف/العنوان/القطعة/المقاس → تحويل أو مسودّة طلب. **لا تزيّف إتمام طلب لا تقدر تنفّذه** |
| 8 | مصطلح لون غامض (نبيتي/غامق) | لا يطابق عائلة مقنّنة مباشرة | طبّق خريطة المرادفات؛ لو ظل غامضاً اسأل |
| 9 | خارج الموضوع / إساءة / حسّاس | تصنيف نية | ابقَ ضمن هوية البراند، تجنّب بلطف أو صعّد |
| 10 | رسالة صوتية | نوع المرفق = audio | لا يمكن معالجتها إلا بإضافة تفريغ صوتي؛ اعتذر أو فرّغها |
| 11 | عدة رسائل سريعة متتابعة | وصول أكثر من webhook خلال ثوانٍ | **debounce / batch** قبل الرد (وإلا يرد البوت ٥ مرات) |
| 12 | خلط لغوي (لهجة/إنجليزي/عربيزي) | كشف اللغة | ردّ بلغة/لهجة الزبون |
| 13 | الهلوسة | الوكيل يخترع سعراً/توفّراً | **حاجز صارم:** الأسعار والتوفّر فقط من قاعدة المعرفة؛ ما تعرفه = قُل لا أعرف / صعّد. لا تخترع أبداً |
| 14 | زبون عائد | `subscriber_id` معروف سابقاً | استرجع التاريخ والتفضيلات |
| 15 | التحويل لإنسان | صريح ("بدي حدا") أو ضمني (شكوى/ثقة منخفضة) | علامة `human_agent` (نافذة ٧ أيام) + إشعار المدير + **إيقاف البوت** لهذا الزبون |
| 16 | نتائج كثيرة جداً | تطابق > ٥ منتجات | أرسل أفضل ٣–٥ + "أشوفلك أكثر؟" |
| 17 | webhook مكرر / معاد المحاولة | نفس معرّف الرسالة | **idempotency**: تجاهل المكرر لتجنّب ردّ مزدوج وكلفة مضاعفة |
| 18 | انتهاء رابط الصورة المؤقت | رابط CDN منتهٍ | نزّل/عالج فوراً عند الوصول؛ أعد الاستضافة عند الحاجة |
| 19 | معلومات شخصية (هاتف/عنوان للـ COD) | كشف PII | خزّن بأمان والتزم بالخصوصية |

## 7. حلقة عمل الوكيل (Agent Loop) — كيف تتجمّع القطع

تسلسل معالجة رسالة واحدة:

1. **استقبال:** ManyChat External Request → `POST { subscriber_id, text, last_image_url, ad_ref, message_id, … }`.
2. **حماية:** فحص idempotency (هل عالجنا `message_id`؟) + إن كانت رسائل سريعة، debounce.
3. **تحميل السياق:** التاريخ + حالة الجلسة من Postgres.
4. **إن وُجدت صورة:** نزّلها → Claude vision → استخرج الصفات (+ embedding اختياري).
5. **بناء النداء:** system prompt (الشخصية/القواعد/الحواجز من إعدادات السلوك) + سياق المعرفة + التاريخ + المدخل الحالي.
6. **القرار (Tool Use):** Claude يختار `search_products` / `check_availability` / `get_media` / `escalate` / `capture_order` / يجاوب مباشرة.
7. **تنفيذ الأدوات:** استعلام Postgres → أعِد النتائج لـ Claude.
8. **الصياغة:** Claude يكتب الرد النهائي + أي منتجات تُعرض.
9. **التنسيق:** Backend يبني Dynamic Block v2 (نص + معرض cards + quick replies + actions مثل tag/notify).
10. **الحفظ:** خزّن الدور (تحديث التاريخ + حالة الجلسة).
11. **الإرجاع:** JSON → ManyChat يعرضه للزبون. مع **fallback JSON** جاهز لو فشل أي شيء.

## 8. أدوات الوكيل (Tool Schema)

| الأداة | المدخلات | ترجع / تفعل |
|---|---|---|
| `search_products` | `color? type? max_price? size? occasion? free_text?` | منتجات مطابقة (المسار 1) |
| `find_similar_by_image` | `attributes` أو `embedding` | منتجات مشابهة بصرياً (المسار 2) |
| `check_availability` | `product_id, size?, color?` | حالة التوفّر |
| `get_product_media` | `product_ids[]` | روابط الصور لبناء المعرض |
| `escalate_to_human` | `reason` | علامة + إشعار المدير + إيقاف البوت |
| `capture_lead_or_order` | `name, phone, address, product, size` | مسودّة طلب COD |

كل أداة = استعلام/فعل عندك. وصْف الأدوات بدقّة لـ Claude هو ما يحدّد جودة قراراته.

## 9. ضبط التكلفة والجودة

- **تدرّج النماذج:** Haiku للتصنيف واستخراج الصفات، Sonnet للمحادثة.
- **فهرسة لا تكرار:** استخرج صفات الكتالوج مرة عند الإضافة، لا عند كل طلب.
- **تخزين مؤقت للسياق:** الكتالوج والـ system prompt ثابتان نسبياً، فلا تعيد بناءهما كل مرة.
- **مجموعة اختبار (eval):** اجمع ٢٠–٣٠ سؤالاً حقيقياً من زبائنك واختبر الوكيل عليها بعد كل تعديل.
- **الحواجز:** ضعها في الـ system prompt + كقيود على الأدوات (مثلاً: السعر يأتي فقط من نتيجة `search_products`، لا من النص الحر).

---

## 10. خارج النطاق الآن (لإبقائه minimal)

لا بوّابة دفع إلكتروني، لا لوحة تحليلات معقّدة. ابدأ ببحث الصفات فقط وأجّل الـ embeddings/التشابه البصري. اجعل التحويل لإنسان مجرد "إشعار المدير" في البداية قبل بناء تدفّق تسليم كامل.
